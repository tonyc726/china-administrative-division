# Spike：村级（level 5）活更新源可行性

> ⏱️ **限时调研（time-boxed spike）**，目的是回答一个问题：**后 stats.gov.cn 时代，村/居委会级（level 5）数据是否存在可持续的"活"更新源？** 结论先行：**不存在单一官方活源**；村级增量应走既有 **Patch 通道**，而非新建村级爬虫。

## 1. 背景与约束

- 12 位区划码结构 `2+2+2+3+3`，level 5 = 村委会/居委会（约 62 万条，NBS 2023 基线）。
- `stats.gov.cn`（统计用区划 + 城乡划分代码，唯一含村级的官方全量源）自 2024 起停止公开发布，2026 转向「国家地名信息库」(dmfw)。
- 因此村级"活更新"的前提是：找到一个**覆盖 level 5、持续更新、可程序化获取、带 GB2260 码**的源。

## 2. 经验探针（本仓实测）

| 探针 | 命令 | 结果 |
|---|---|---|
| dmfw 是否含村级 | `getList?code=110101001000`（东华门街道，level 4） | **子级数 = 0** → dmfw 止于 level 4，**无村级** |
| dmfw 层级深度 | 宁夏全量 `--maxLevel=4`（M4 实跑） | 252 节点止于乡镇/街道，无 level 5 |

> 即：**dmfw（后 stats 时代唯一的官方"活"源）结构性地不含村级。** 这不是抓取深度问题，是数据源本身不覆盖。

## 3. 候选源评估

| 候选源 | 覆盖村级 | 活更新 | 程序化 | 带 GB2260 码 | 授权 | 结论 |
|---|:--:|:--:|:--:|:--:|:--:|---|
| 国家地名信息库 dmfw | ✗ | ✓ | ✓(JSON) | ✓ | 公开 | 结构无村级，**不可用于 L5** |
| NBS 2023 基线(本仓) | ✓(62万) | ✗(冻结) | ✓ | ✓ | 公开 | 只能作**冻结地板**，无增量 |
| stats.gov.cn 城乡划分代码 | ✓ | ✗(已死) | — | ✓ | — | 源已停更 |
| 高德/百度/天地图 POI | 部分(社区POI) | ✓ | ✓(需Key) | ✗(无区划码) | 受限/计费 | 无 GB2260 码、非权威，仅可做**存在性旁证** |
| 各地民政局公示 | ✓(局部) | ✓ | ✗(非结构化公告) | 部分 | 公开 | 碎片化、需 NLP 抽取，**非全量源** |
| 第三次国土调查/自然资源部 | ✓ | 周期性 | ✗(无公开API) | 部分 | 受限 | 不可程序化获取 |
| 开源数据集(modood/xiangyuecn 等) | ✓ | ✗ | ✓ | ✓ | 公开 | 均派生自同一冻结的 stats 2023，**无独立增量** |

## 4. 结论

- **不存在单一的、官方的、可持续更新的村级活源。** 所有"全量带码"的村级数据都派生自已冻结的 stats.gov.cn 2023 快照。
- POI 类源有"活"的新社区信号，但**无 GB2260 码、非权威**，只能做存在性旁证（shadow）。
- 各地公示有真实增量，但**碎片化、非结构化**，需要抽取。

## 5. 推荐架构（村级 = Patch 驱动，非爬虫驱动）

v2 架构**已具备**正确机制——无需新建村级爬虫：

```
冻结地板：NBS 2023 村级(62万, source_type=official_nbs)
        │
        ├── 村级增量 → 既有 Patch 通道 (patches/<YYYY>/, apply-patch)
        │     ├─ 来源①：各地民政局公示 → NLP 变更提取器（旁支③）产出 draft Patch
        │     │           (source_type=mca_decree / community)
        │     └─ 来源②：POI 交叉验证新社区存在性 → shadow-map 置信度
        │           (source_type=shadow_map，需人工/多源确认后升级)
        └── validatePatch 守门 + 置信度分级(official_nbs>mca_decree>community>shadow_map)
```

**关键洞察**：村级"活更新"的本质是**变更事件**（撤并/新设社区/更名），而非可全量轮询的目录。变更事件天然适配 Patch 协议（增量、带证据、带置信度、可审计），这正是 v2 已实现的 `apply-patch` 闭环。

## 6. 决策建议

1. **不新建村级爬虫**（无可爬的活源；爬 POI 得不到带码权威数据，违反 Occam）。
2. 以 **NBS 2023 村级为冻结地板**，村级变更全部走 **Patch 通道**。
3. 优先投入**旁支③ NLP 变更提取器**：把"各地公示"这一碎片化但真实的增量源，转成结构化 draft Patch（这是村级增量的最高 ROI 入口）。
4. POI 仅作 `shadow_map` 置信度的**存在性旁证**，不作为权威码源；引入与否取决于是否需要"发现"新社区（可后置）。

> 一句话：**村级不是"再找一个源去爬"的问题，而是"把变更事件接进 Patch 闭环"的问题——机制已就绪，缺的是喂入口（NLP 提取器）。**
