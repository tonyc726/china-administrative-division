# 中国行政区划数据架构重构与主权数据治理深度研究报告

## 1. 战略背景与核心挑战 (Strategic Context)

### 1.1 "后统计局时代"的数据断供危机

在 2024 年 10 月之前，中国行政区划数据的获取主要依赖于一条单一且权威的管道：**国家统计局（NBS）**每年发布的《统计用区划代码和城乡划分代码》。这条管道为无数的电商物流系统、政务数据交换平台以及人口统计学研究提供了基础的 **12 位代码标准**。

然而，随着 2024 年 10 月国家统计局停止公开细分代码数据，这一生态系统遭遇了前所未有的 **"黑天鹅"** 事件。

> **当前时间节点**：2026 年，距离最后一次官方全量数据更新（2023 版）已过去近三年。

这三年期间，中国的行政区划发生了频繁且微小的变动：
- 撤县设区
- 乡镇合并
- 街道拆分
- 村级自治组织的重组

旧有的爬虫逻辑（Legacy Crawler Logic）基于固定的 URL 结构和 HTML 表格解析，面对不再更新的 `stats.gov.cn` 已彻底失效。

对于 @cn-division 项目的重构而言，这不仅是技术栈的升级，更是**数据治理模式的根本转型**。项目必须从"被动镜像官方数据"转型为"主动合成多源情报"。

新的架构必须具备极强的**抗打击能力**，能够在没有单一真理源（Single Source of Truth）的情况下，通过以下渠道重建高置信度的 12 位行政区划数据库：
- 民政部通报
- 商业地图 API 的影子数据
- 社区的分布式修订

### 1.2 架构重构的核心目标：解耦与主权

除数据源危机外，原有项目架构也面临严重工程挑战。传统的将数十兆甚至上百兆的 JSON/CSV 数据直接提交到 Git 仓库的做法，导致了严重的**仓库膨胀（Repo Bloat）**，使得 `git clone` 变得缓慢且昂贵。

本次重构的核心哲学是：**"代码与数据解耦"（Code-Data Decoupling）**

具体而言，@cn-division 仓库将退化为一个**纯粹的逻辑容器**，仅包含：
- Schema 定义
- CLI 工具链
- 校验算法
- 数据合成流水线

真正的**数据资产（Data Assets）**将作为独立版本化的实体，存储于 **NPM Registry** 这一全球分发网络之上。

这种架构设计的精妙之处在于：

| 特性 | 说明 |
|------|------|
| **分发效率** | 用户在只需校验逻辑时（如前端表单验证），无需下载庞大的历史数据集 |
| **版本流动性** | 通过 CLI 工具，用户可以精准"水合"（Hydrate）特定年份的数据（如仅需 2021 年数据用于审计），而无需受制于 Git 的历史树 |
| **社区主权** | 数据不再是只有 Repo Owner 有权提交的静态文件，而是通过 Patch 协议由社区共同维护的动态账本 |

本报告将详细论述：
1. 转型背后的技术实现路径
2. 数据治理策略
3. 应对未来不确定性的防御性编程方案

## 2. 架构设计：基于 NPM 的数据湖与工作空间模式 (Architectural Design)

为了实现"源码不含数据，数据本地生成"的目标，我们需要构建一个以 **NPM Workspaces** 为基础的 **Monorepo** 架构。

这不仅是为了模块化，更是为了构建一条清晰的"数据生产供应链"。

### 2.1 Monorepo 拓扑结构设计

采用如下包结构，清晰分离核心逻辑、工具链与数据定义：

| Package Scope | Role & Responsibility | Dependency Constraints |
|---------------|----------------------|------------------------|
| `@cn-division/core` | 核心逻辑层。包含 12 位代码的 TypeScript 类型定义、校验算法（如 Luhn 算法变体）、层级推导逻辑 | **零依赖（Zero-dependency）**。必须极其轻量（< 5KB），以便随处运行 |
| `@cn-division/cli` | 编排控制层。负责数据的下载（Hydration）、缓存管理、Patch 应用以及 CSV 导出 | 依赖 `cacache`, `tar-stream`, `better-sqlite3` 等 |
| `@cn-division/crawler` | 情报采集层。包含针对民政部 PDF、地图 API 的各类针对性爬虫和解析器 | 依赖 `puppeteer`, `cheerio`, `pdf-parse` 等重型库，仅开发阶段使用 |
| `@cn-division/data-protocol` | 协议定义层。定义 Patch 文件的 JSON Schema、数据源的置信度评分标准 | 被 CLI 和 Crawler 共同引用 |

这种结构确保了最终用户在集成验证功能时，不会引入 CLI 或爬虫的庞大依赖树。

### 2.2 数据分发新范式：NPM as a Data Lake

传统的 NPM 包通常包含代码和少量资源文件。但在本架构中，我们将发布一系列特殊的"数据包"（Data Packages），例如 `@cn-division/source-2023` 或 `@cn-division/source-2025-patch`。

这些包具有以下特征：
- **无入口文件**：`package.json` 中没有 `main` 字段
- **仅包含压缩数据**：主体是经过高度压缩的二进制或 Protocol Buffers 文件，而非明文 CSV，以绕过 NPM 的发布体积限制并提高传输效率
- **版本语义异化**：其版本号（如 `1.0.0`）不代表功能迭代，而代表数据的"修正版本"

#### 新用户的启动流程模拟

```bash
# 1. 克隆并安装工具链
git clone https://github.com/cn-division/division.git
npm install
# 此时，本地没有任何区划数据文件

# 2. CLI 初始化（水合数据）
npx cn-div hydrate --year 2025
# 该命令触发 @cn-division/cli 的下载模块
```

### 2.3 技术深究：程序化 Tarball 获取与流式解压

要求用户"通过 CLI 从 NPM 下载数据"意味着我们**不能依赖常规的 `npm install`**，因为这会将数据锁死在 `node_modules` 中，且无法灵活控制下载策略（如断点续传或缓存复用）。

我们需要实现一个自定义的 **NPM Tarball Fetcher**。

#### 2.3.1 绕过 Package Manager 的元数据查询

CLI 首先通过 NPM Registry API 查询目标包的元数据：

```http
GET https://registry.npmjs.org/@cn-division/source-2025
```

**Response 分析**：返回的 JSON 中，`dist.tarball` 字段包含了 `.tgz` 文件的绝对下载地址；`dist.shasum` 提供了完整性校验哈希。

> **鉴权要求**：此过程必须支持鉴权（Auth Token），因为某些高精度修正数据可能是发布在私有 Scope 下的（针对企业级用户）。CLI 需自动读取用户环境中的 `.npmrc` 配置。

#### 2.3.2 流式管道设计 (Streaming Pipeline)

下载 100MB+ 的历史数据压缩包时，**绝不能将其完全读入内存**。必须构建一个纯流式的处理管道：

```typescript
import { pipeline } from 'stream/promises';
import got from 'got';
import tar from 'tar-stream';
import { createGunzip } from 'zlib';

async function hydrateData(version: string) {
  const tarballUrl = await getNpmTarballUrl(`@cn-division/source-${version}`);
  const extract = tar.extract();

  extract.on('entry', (header, stream, next) => {
    if (header.name.endsWith('.csv')) {
      // 直接将流导向本地 SQLite 导入器，不落地临时文件
      stream.pipe(sqliteImporter).on('finish', next);
    } else {
      stream.resume(); // 丢弃非数据文件
      next();
    }
  });

  await pipeline(
    got.stream(tarballUrl), // HTTP 下载流
    createGunzip(),         // 解压流
    extract                 // Tar 提取流
  );
}
```

这种设计确保了即便在内存受限的 CI/CD 环境（如 GitHub Actions Free Runner）中，也能稳定处理 GB 级的历史全量数据。

## 3. "暗区"生存指南：2024-2026 数据获取替代方案研究

鉴于 NBS 数据的断供，我们必须构建一个**多源情报融合系统**。该系统将不再寻求单一的完美数据源，而是通过**交叉验证（Cross-Validation）**来逼近真实情况。

### 3.1 替代源深度评估

#### 3.1.1 民政部（MCA）行政区划变更公报

| 维度 | 说明 |
|------|------|
| **数据性质** | 最高置信度，但低频、低粒度 |
| **获取方式** | 民政部官网发布的《中华人民共和国行政区划简册》或不定期的"国务院批复"公告 |
| **局限性** | 通常只披露县级以上（Level 3）及部分乡镇级（Level 4）的变更（撤县设区、更名） |
| **严重缺失** | 几乎从不披露村级/居委会（Level 5）的变动信息 |
| **格式** | 非结构化：多为 PDF 文件或叙述性 HTML 文本（例如："同意撤销 A 镇，设立 B 街道，管辖原 A 镇的...区域"） |

**技术对策**：开发基于 NLP 的**变更指令提取器（Change Operation Extractor）**。通过正则模版识别"撤销...设立..."、"合并...到..."等关键词，自动生成结构化的 Patch 操作指令。

#### 3.1.2 商业地图 API 的影子数据

| 维度 | 说明 |
|------|------|
| **数据性质** | 中等置信度，高时效性，高粒度 |
| **来源分析** | 高德地图 (Amap)：其 district 搜索接口提供 adcode（6 位）和 citycode。在查询街道（Level 4）时，往往能在 districtList 中返回较为完整的列表 |
| | 腾讯地图 (Tencent Map)：get_district 接口在某些省份的数据更新速度快于高德，特别是南方省份 |
| | 天地图 (Tianditu)：作为国家测绘地理信息局建设的平台，其行政区划数据（特别是边界）在法律上最具参考性，但 API 访问往往受限或需要政府级 Key |

**数据清洗挑战**：
- **名称不规范**：地图数据常包含通俗名（如"开发区"而非"XX 经济技术开发区管委会"）
- **编码缺失**：地图 POI 通常不通过 12 位统计用代码索引，而是使用内部 ID 或 6 位行政码

**对策**：建立**名称-代码映射库**。利用 2023 年的全量数据建立基准，通过"模糊匹配"（Fuzzy Matching）将地图 API 返回的新增地名映射到可能的代码段上。

例如，若在一个已知的县级单元下发现一个新的街道名，且该县级单元的乡镇代码序列中有空缺，则可推测其代码。

#### 3.1.3 地方统计局公报与"零散情报"

| 维度 | 说明 |
|------|------|
| **数据性质** | 高置信度，但极度碎片化 |
| **来源** | 各省、市统计局官网偶尔会发布的《统计用区划代码和城乡划分代码》的局部更新 |
| **利用方式** | 这无法通过通用爬虫获取，必须依赖**社区贡献（Crowdsourcing）** |

### 3.2 社区维护模式：分布式补丁协议 (The Distributed Patch Protocol)

由于没有任何单一爬虫能填补 Level 5（村级）的数据空白，项目必须转型为社区驱动模式。但这并不意味着接受随意的 Pull Request。我们需要定义严格的 **Patch Protocol**。

#### 3.2.1 Patch 文件结构定义

所有的变更必须以**原子操作（Atomic Operations）**的形式提交，而非直接修改全量 JSON。这类似于数据库的 Migration 文件。

```json
// patches/2025/310115-pudong-update.json
{
  "meta": {
    "author": "contributor_id",
    "source_url": "http://minhang.gov.cn/announcement/123.pdf",
    "evidence_confidence": "high",
    "apply_after": "2023-baseline"
  },
  "operations": [
    {
      "op": "add",
      "level": 4,
      "parent_code": "310115",
      "code": "310115001",
      "name": "新设立街道办事处"
    },
    {
      "op": "remove",
      "code": "310115102"
    },
    {
      "op": "move",
      "code": "310115103001",
      "new_parent": "310115001"
    }
  ]
}
```

#### 3.2.2 补丁验证与合并策略

1. **语法校验**：CI 流水线首先验证 12 位代码的合法性（如前 2 位是否匹配省份，校验位是否正确）
2. **逻辑冲突检测**：检查 Patch 是否试图删除一个不存在的节点，或者创建一个代码冲突的节点
3. **置信度评分**：系统根据 `source_url` 的域名后缀（`.gov.cn` 权重最高）和贡献者的历史信誉，自动为生成的数据打分。CSV 导出时，用户可以选择过滤掉低置信度的记录

## 4. 极致性能的数据处理与缓存策略 (Data Engineering & Caching)

需求明确指出"构建过程需极致利用缓存"。传统的"下载-解析-转换"流程在面对百万级村级数据时效率极低。我们需要引入数据库技术来作为中间层。

### 4.1 SQLite：本地数据的核心引擎

虽然最终输出是 CSV，但在本地构建过程中，使用 **SQLite** 是最优解。

#### 4.1.1 为什么选择 SQLite？

| 优势 | 说明 |
|------|------|
| **关系型查询能力** | 行政区划本质上是树状结构。重建树结构（如"查询某省下所有变更过的村"）在 SQL 中通过递归查询（Recursive CTEs）极为高效 |
| **文件级缓存** | SQLite 数据库只是一个单文件（`cache.db`）。这比管理数万个细碎的 JSON 文件对文件系统更友好，且更容易通过校验和（Checksum）判断是否需要更新 |
| **内存效率** | Node.js 处理大 JSON 对象极其消耗堆内存。SQLite 允许我们将数据留在磁盘上，仅在流式导出时按需读取，彻底解决 OOM（Out of Memory）问题 |

#### 4.1.2 缓存架构设计

**Layer 1: HTTP Cache (ETag/Last-Modified)**

CLI 在请求 NPM Tarball 时，必须发送 `If-None-Match` 头。NPM Registry 支持标准的 HTTP 缓存协商。如果云端数据未变，服务器返回 304，CLI 直接跳过下载，节省带宽和时间。

**Layer 2: Extraction Cache (Integrity Check)**

下载的 Tarball 会被解压并导入 SQLite。在导入前，CLI 计算 Tarball 的 SHA-512 哈希值并存储在本地 `meta.json` 中。下次运行时，若远端哈希与本地记录一致，则跳过解压和导入步骤。

**Layer 3: Query Result Cache**

对于频繁的查询（如"导出 2023 年全量数据"），CLI 可以将生成的 CSV 文件压缩缓存。只有当底层的 SQLite 数据发生 Patch 变更时，才使该缓存失效。

### 4.2 高性能 CSV 生成流水线

生成全量 CSV（可能超过 70 万行）时，必须使用 **Backpressure-aware Streams**。

**技术实现方案**：
1. **Database Cursor**：使用 `better-sqlite3` 的 `.iterate()` 方法，这会创建一个迭代器而非一次性加载所有行
2. **Transform Stream**：一个自定义的 Node.js Transform 流，负责将 SQL 结果对象转换为逗号分隔字符串，并处理特殊字符转义（如地名中包含逗号）
3. **Write Stream**：管道直接对接文件系统写入流

```javascript
// 核心流式导出逻辑示意
const stmt = db.prepare('SELECT code, name, parent_code FROM divisions WHERE year = ?');
const iterator = stmt.iterate(year);

const readable = Readable.from(iterator);
const transformer = new Transform({
  objectMode: true,
  transform(row, encoding, callback) {
    this.push(`${row.code},"${row.name}",${row.parent_code}\n`);
    callback();
  }
});

await pipeline(readable, transformer, createWriteStream('output.csv'));
```

这种设计保证了无论数据量扩展到多大，**内存占用始终保持在几十 MB 的水平**。

## 5. 遗留系统分析与数据结构演变 (Legacy Analysis & Schema Evolution)

### 5.1 旧爬虫逻辑的考古与批判

旧的 `stats.gov.cn` 爬虫逻辑依赖于统计局网站严格的层级 URL 结构：`index.html` → `省.html` → `市.html`...

**关键特征**：它利用了 HTML 页面的表格结构，直接抓取其中的 12 位代码和名称。

**城乡分类代码**：旧数据的最后一列通常是"城乡分类代码"（如 111 主城区，220 村庄）。

> **演变分析**：自 2024 年起，这部分数据（城乡代码）在公开渠道彻底消失。新架构必须面对这一字段的缺失。

### 5.2 数据 Schema 的防御性演进

为了适应多源数据和不确定的未来，数据 Schema 必须从"扁平结构"演进为"带元数据的时态结构"。

#### 旧 Schema

```json
{ "code", "name", "urban_rural_code" }
```

#### 新 Schema (SQLite Table Definition)

```sql
CREATE TABLE divisions (
    code TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    level INTEGER NOT NULL,       -- 1=省,..., 5=村
    parent_code TEXT,
    year INTEGER NOT NULL,
    status TEXT DEFAULT 'active', -- active, deprecated, suspended
    source_type TEXT,             -- 'official_nbs', 'mca_decree', 'community_patch'
    confidence_score INTEGER DEFAULT 100, -- 100=官方, 50=社区推测
    urban_rural_code TEXT         -- 可空，标记为 legacy
);
```

#### 兼容性策略

在导出 CSV 时，CLI 应提供 `--legacy-format` 选项。如果用户需要旧格式，系统将 `urban_rural_code` 留空或填入默认值（如根据 level 推断，Level 5 默认为 220），并输出警告日志。

这保证了旧有的下游系统不会因为缺少列而崩溃，但也**明确传达了数据精度的下降**。

## 6. 法律合规与数据主权声明 (Compliance & Sovereignty)

在设计重构方案时，必须严肃对待中国的《测绘法》及相关数据安全法规。

### 6.1 坐标数据的红线

项目必须严格遵守**"只做代码，不做坐标"**的原则。

**风险点**：抓取并发布含有高精度经纬度（特别是未经 GCJ-02 加密的原始坐标）的数据可能被视为非法测绘或涉密。

**设计决策**：@cn-division 的核心数据库**绝不存储经纬度信息**。如果用户需要坐标，应通过插件机制在用户本地调用地图 API 自行获取。这不仅规避了法律风险，也减轻了维护数据的负担。

### 6.2 统计数据的版权与使用

统计局公开的数据在原则上属于公共信息，但对其进行加工、汇编形成的产品具有著作权属性。

**许可协议**：建议项目采用 **CC-BY-SA 4.0** 或 **ODbL（Open Database License）**。

这明确了下游用户在使用数据时必须回馈社区（Share Alike），即如果他们发现了数据错误并修正，必须将修正回馈给上游，这正是维持"社区补丁模式"生命力的法律基础。

## 7. 实施路线图 (Implementation Roadmap)

| 阶段 | 时间 | 主要任务 |
|------|------|----------|
| **Phase 1: 基石构建** | M0-M1 | 初始化 Monorepo，完成 CLI 的流式下载与 SQLite 导入功能。将 2023 年最后一份官方数据清洗并打包发布为 `@cn-division/source-2023` (v1.0.0)。这是项目的"冷启动"资产 |
| **Phase 2: 补丁系统上线** | M2-M3 | 定义并冻结 Patch JSON 规范。在 GitHub 建立 patches 仓库，设立 CI 校验流水线。发布 2024 年的"推测性数据包"，包含基于民政部公告整理的第一批补丁 |
| **Phase 3: 自动化与生态** | M4+ | 开发辅助爬虫，监控民政部官网变动并自动发起 Pull Request。建立与 OpenStreetMap 中文社区的合作，尝试交换非坐标类的行政变更情报 |

通过这一系列的重构，@cn-division 将从一个简单的爬虫脚本进化为一个**抗脆弱（Antifragile）**的分布式数据基础设施。

即使在官方数据长期缺位的背景下，依靠架构的灵活性和社区的集体智慧，依然能够为中文互联网提供最可信的行政区划服务。
