# 项目改造实施计划

> 📐 **历史设计稿（仅存档）**：本文为 v2 规划期的实施计划，其中目录结构、`source-history` 等命名为早期设想，部分**已被实现取代**。权威的仓库结构与用法以根 [`README.md`](../README.md#monorepo-结构) 为准。

**目标**：将现有的大型单体 JS 爬虫项目迁移至基于 NPM 分发的现代化 TypeScript Monorepo 架构

**当前状态**：
- **代码**：遗留的 JavaScript 爬虫脚本 (`scripts/*.js`)
- **数据**：`data/GB2260/*.json.gz` (1980-2021 多年份历史数据) 及 `data/stats.gov.cn/`
- **缓存**：`pageCacheDB/` (LevelDB 二进制大文件)

---

## 第一阶段：环境准备与资产提取 (Phase 1: Preparation)

**目标**：搭建支持 TypeScript 的 Monorepo 脚手架，并将旧项目归档以便提取资产。

### 1.1 归档旧项目 (The Move)

在初始化新环境之前，必须先将旧的"单体应用"隔离。我们将原有的配置文件和依赖描述文件也一并移入 legacy，以确保旧脚本在需要时仍能独立运行。

在根目录执行：

```bash
# 1. 创建归档目录
mkdir -p legacy

# 2. 移动旧代码、数据、日志、缓存
# 注意：package.json 和 lock 文件也要移动，因为它们属于旧的运行环境
mv scripts data pageCacheDB logs legacy/
mv package.json package-lock.json pnpm-lock.yaml legacy/ 2>/dev/null || true
mv README.md LICENSE legacy/ 2>/dev/null || true

# 3. 此时根目录应该几乎为空（除了 .git 和 legacy 目录）
ls -F
# 预期输出: legacy/  .git/
```

### 1.2 初始化 Monorepo 环境

现在你有了一个干净的根目录，可以初始化现代化的工作区了。

```bash
# 1. 初始化全新的根目录 package.json
pnpm init

# 2. 修正 package.json 配置
# 设置为 module 类型，并标记为 private (Monorepo 根不发布)
npm pkg set type="module"
npm pkg set private=true
npm pkg set name="@cndiv/monorepo"

# 3. 创建工作区配置文件 pnpm-workspace.yaml
# 我们把 legacy 也加入工作区，方便统一管理依赖，但保持物理隔离
echo "packages:\n  - 'packages/*'\n  - 'legacy'" > pnpm-workspace.yaml

# 4. 安装全新的全局开发依赖 (DevDependencies)
# 这些工具将服务于整个仓库
pnpm add -D -w typescript @types/node tsx tsup eslint eslint-config-prettier prettier

# 5. 初始化全局 tsconfig.json
npx tsc --init --target ES2022 --moduleNodeNext true --module NodeNext
```

### 1.3 建立目录结构

创建新的 `packages` 目录，所有新代码强制使用 TypeScript：

```
.
├── packages/
│   ├── core/           # [新建] 核心算法与类型定义 (src/index.ts)
│   ├── data-protocol/  # [新建] Schema 定义 (src/index.ts)
│   ├── cli/            # [新建] 命令行工具 (src/cli.ts)
│   └── crawler/        # [重构] 参考 legacy/scripts 逻辑，用 TS 重写
├── legacy/             # [归档] 旧项目容器
│   ├── package.json    # [迁移] 旧的依赖配置 (cheerio, leveldown 等)
│   ├── scripts/        # [迁移] 旧 JS 源码
│   └── data/           # [迁移] 旧 JSON 数据
├── pnpm-workspace.yaml # [新建]
├── package.json        # [新建] 仅包含 build 工具
├── tsconfig.json       # [新建]
└── ...
```

### 1.4 恢复旧环境 (可选)

如果你需要运行旧脚本来对比数据或调试：

```bash
# 由于 legacy 被加入了 pnpm-workspace.yaml
# 在根目录执行 install 会自动安装 legacy/package.json 中的依赖
pnpm install

# 运行旧脚本 (在 legacy 目录下)
cd legacy
npm run gb2260:crawler
```

## 第二阶段：核心包开发 (Phase 2: Core Implementation)

**目标**：使用 TypeScript 实现新架构的基础设施。

### 2.1 @cndiv/data-protocol

定义强类型的行政区划结构，确保全链路类型安全。

**文件**：`packages/data-protocol/src/schemas/division.schema.ts`

**内容**：

```typescript
export interface Division {
  code: string;       // 12位代码
  name: string;       // 名称
  level: number;      // 1:省, 2:市, 3:县, 4:乡, 5:村
  parent_code: string | null;
  year: number;       // 关键字段：区分不同年份的数据
  // 扩展字段
  province_code?: string;
  city_code?: string;
  county_code?: string;
}
```

### 2.2 @cndiv/cli (数据迁移器)

编写 TS 脚本 `packages/cli/src/scripts/migrate-legacy.ts`，逻辑如下：

| 步骤 | 说明 |
|------|------|
| **扫描源目录** | 遍历 `legacy/data/GB2260/` 目录，匹配所有 `(\d{4}).json.gz` 文件 |
| **流式处理** | 使用 `zlib.createGunzip()` 解压文件流 |
| **解析 JSON 内容** | 注意：旧数据可能是树状结构，需递归拍平 |
| **数据清洗** | 将拍平后的数据映射到 Division 接口 |
| **补充 year 字段** | 取自文件名 |
| **计算 level** | 根据代码规则 |
| **批量入库** | 将清洗后的数据写入 SQLite (`dist/source-history.db`) |

## 第三阶段：数据迁移实战 (Phase 3: Data Migration)

**目标**：将 1980-2021+ 的全量历史数据转换为标准 SQLite 格式。

### 3.1 执行 TS 迁移脚本

使用 tsx (TypeScript Execute) 直接运行迁移脚本，无需预编译：

```bash
# 在根目录运行
pnpm --filter @cndiv/cli exec tsx src/scripts/migrate-legacy.ts \
  --input-dir ../../legacy/data/GB2260 \
  --output ./dist/source-history.db
```

### 3.2 验证数据完整性

编写测试脚本 `verify.ts`：

| 验证项 | 说明 |
|--------|------|
| **总量核对** | 查询 SQLite 中每年份的记录数，与旧 JSON 的 key 数量对比。例如：`SELECT count(*) FROM divisions WHERE year=2020` vs `Object.keys(json2020).length` |
| **抽样检查** | 确保 1980 年的老旧数据和 2021 年的新数据均已正确存入，且乱码问题（如有）已处理 |

### 3.3 打包发布数据

创建 `@cndiv/source-history` 包（包含所有历史年份）：

```bash
mkdir -p packages/source-history/data
# 将生成的全量历史数据库放入
cp packages/cli/dist/source-history.db packages/source-history/data/data.db
```

> **注**：对于 2023/2024 等较新的数据，后续建议按年份单独发包（如 `@cndiv/source-2024`），以减小用户下载体积。

## 第四阶段：清理与发布 (Phase 4: Cleanup & Release)

**目标**：彻底清理遗留的 JS 代码和二进制大文件。

### 4.1 历史大文件清理 (高危操作)

确认 TS 重构完成且数据无误后，执行核弹级清理：

```bash
# 1. 移除 pageCacheDB (LevelDB 缓存，不再需要)
git filter-repo --path pageCacheDB/ --invert-paths --force
# 注意：如果它们现在在 legacy/pageCacheDB，路径需相应调整
git filter-repo --path legacy/pageCacheDB/ --invert-paths --force

# 2. 移除旧的 JSON Gzip 数据 (已迁移至 SQLite npm 包)
git filter-repo --path data/ --invert-paths --force
git filter-repo --path legacy/data/ --invert-paths --force

# 3. (可选) 移除旧 JS 脚本，如果确认不再需要参考
# git filter-repo --path legacy/scripts/ --invert-paths --force
```
